# Decisions

One dated line per non-obvious choice. Newest at the bottom.

- 2026-11-13 — Input lives in `fossps-input`, a crate with no platform dependencies, so the dedicated server, replays and tests use the same `InputFrame` without linking a window system.
- 2026-11-13 — Windowing is winit 0.30 and gamepads are gilrs 0.11, both behind the `window` feature of `fossps` (on by default) so a headless build links neither.
- 2026-11-13 — Keys are bound by physical position, not by the letter printed on them, so WASD works on AZERTY and Dvorak.
- 2026-11-13 — Gamepad buttons are named by position (`GamepadSouth`), not by Xbox or PlayStation labels.
- 2026-11-13 — An action has one of three kinds (button, 1D axis, 2D axis). No Unreal-style modifier and trigger stacks: too much to learn for the "Easy" pillar.
- 2026-11-13 — `look` is one action with two readings: mouse movement in raw counts (`delta`, never scaled by time) and stick tilt as a rate (`axis2d`). The game applies a separate sensitivity to each.
- 2026-11-13 — When several bindings drive one axis the strongest wins; they are not added, so keyboard plus stick is never faster than either.
- 2026-11-13 — Sticks use a circular scaled dead zone (inner 0.15, outer 0.95); triggers press at 0.5 and release at 0.4. gilrs's own filters are off so shaping happens once, in testable code.
- 2026-11-13 — Presses are latched per button between ticks: a tap shorter than a tick still counts once, and extra ticks in one frame do not repeat it.
- 2026-11-13 — A missing gamepad or keyboard binding is a startup warning, not an error, so a half-finished prototype still runs.
- 2026-11-13 — All connected gamepads feed one player; the active pad is the one last pushed firmly (past half way), so drift on an idle pad cannot take over. Gamepad input is ignored while the window is unfocused.
- 2026-11-13 — Simulation defaults to 60 ticks per second, with at most 5 catch-up ticks per frame and stalls over 250 ms dropped.
- 2026-11-13 — Until the renderer exists the main loop sleeps until the next tick, and `softbuffer` fills the window with a solid colour because Wayland hides windows that have drawn nothing. Both are replaced in #2. (Done: superseded by the renderer entries below.)
- 2026-11-13 — Escape always frees the mouse (and still reaches the action map); the click that captures the mouse is not passed to the game.
- 2026-11-13 — The renderer is its own crate, `fossps-render`, on `ash` 0.38 with the `loaded` feature: raw Vulkan handles stay reachable for FSR, and building needs no Vulkan SDK because the library is found at startup.
- 2026-11-13 — Shaders are WGSL compiled to SPIR-V by `naga` in `build.rs`: pure Rust, so no `glslc` or SDK to install. Revisit if a technique needs something naga cannot express.
- 2026-11-13 — Dynamic rendering and synchronization2 (both core in Vulkan 1.3) are required from the start; there are no render pass or framebuffer objects.
- 2026-11-13 — GPU choice: dedicated over built-in over software, first listed wins a tie. When none qualifies the error lists every card with its reason.
- 2026-11-13 — `vsync` (default on) is the one display setting: on is FIFO; off is MAILBOX, else IMMEDIATE, else FIFO. No frame limiter yet.
- 2026-11-13 — Frames are drawn in `RedrawRequested`, requested after each loop pass. Acquiring an image times out after 100 ms and a skipped frame pauses drawing for 250 ms, so a hidden window cannot stall the simulation.
- 2026-11-13 — The swapchain is rebuilt on resize or `OUT_OF_DATE` only, never on `SUBOPTIMAL` alone, which can persist and cause a rebuild loop.
- 2026-11-13 — The triangle is tested by drawing it without a window and checking pixels. The test skips where Vulkan 1.3 is missing unless `FOSSPS_REQUIRE_VULKAN=1`, which Linux CI sets after installing lavapipe.
- 2026-11-13 — Scripting is its own crate, `fossps-script`, on `mlua` 0.12 with the `luau` feature. Luau is compiled from source, so building now needs a C++ compiler.
- 2026-11-13 — Scripts get a ready-made `game` global instead of `require("fossps")`: one line less to learn, and the Luau language server types globals from one definitions file with no per-project setup.
- 2026-11-13 — Scripts register functions (`game.onTick(function(step) ... end)`) rather than defining magic global names like LÖVE's `love.update`: a misspelled name is an error with a suggestion instead of silence, and editors can type the handler's arguments.
- 2026-11-13 — Reading a member of `game` that does not exist is an error naming the closest real one; `game` is read-only.
- 2026-11-13 — Each reload runs the saved file in a brand-new sandboxed VM. Script variables reset; engine state is untouched. `onStart` does not run again, `onReload` does. Keeping chosen script values across reloads is a follow-up.
- 2026-11-13 — A reload that fails keeps the previous version running. A runtime error in one handler is reported once per version and the other handlers keep running.
- 2026-11-13 — Saves are found by checking the file's time and size every 100 ms, and loaded once two checks agree. No file-watcher dependency: polling behaves the same on every platform and with editors that save by rename.
- 2026-11-13 — One call into a script may run for 1 second and a script may use 256 MB. A script stopped for running too long is paused until the next save, so an endless loop cannot freeze the game on every tick; catching the stop with `pcall` does not avoid it.
- 2026-11-13 — `require` is not available yet (a game is one `main.luau`); calling it says so. Multi-file games are a follow-up.
- 2026-11-13 — `fossps <folder>` plays the game in that folder, and plain `fossps` plays the current folder if it has a `main.luau`; otherwise it shows the input demo. #4 replaces this with `fossps run`.
- 2026-11-13 — The command line is parsed by `clap` (help text and "did you mean" for free), behind a `cli` feature so a game written in Rust against the library does not build it. `fossps` alone prints help and succeeds; the old `fossps <folder>` form is gone in favour of `fossps run [folder]`, and the input demo is `fossps demo`.
- 2026-11-13 — `fossps new <folder>` never asks questions, never overwrites (an empty folder is fine, one with files is refused) and does not run `git init`: a tutorial command must behave the same for everyone, and git may not be installed.
- 2026-11-13 — A new game is four files: `main.luau`, `README.md`, `fossps.d.luau` and `.vscode/settings.json` (luau-lsp `platform.type: standard` plus `types.definitionFiles`, the map form current in luau-lsp 1.70). No `.luaurc` or `.gitignore`: neither does anything yet, and every extra file is one more thing to wonder about.
- 2026-11-13 — Game names may have spaces, capitals and non-English letters; only what breaks a folder name on some platform is refused (Windows' forbidden characters and reserved names, a leading dash or dot, trailing dot or space, over 64 characters).
- 2026-11-13 — `fossps run` rewrites a game's `fossps.d.luau` when it differs from the engine's, and says so: the file is the engine's, and stale autocomplete after an upgrade is worse than a rewritten generated file. A game without the file does not get one.
- 2026-11-13 — `examples/hello/main.luau` is the template with the name filled in, held equal by a test, so the example in the repo cannot drift from what `fossps new` writes.
- 2026-11-13 — A graphical editor is planned as the last milestone (M5, #38–#44), after the engine ships. It stays inside the Focused pillar: FPS maps and game modes only, a mode of the same binary (`fossps edit`), levels stay plain glTF with entities in a text file beside them, and no CSG brushes, terrain, material graphs or visual scripting.
- 2026-11-13 — The editor is kept easy by three rules (#46–#53): the game mode tells you what the map still needs, tools use the player's own measurements and controls, and anything advanced is an overlay or a search away rather than a permanent panel. These ideas were not checked against prior art when filed; each issue does that first.
- 2026-11-13 — New games ship a `CLAUDE.md` and a `.claude/settings.json` that pre-approves only `fossps check`. The guide points at `fossps.d.luau` as the one list of what exists, so it does not go stale when the API grows; unlike that file it belongs to the game's author and is never rewritten.
- 2026-11-13 — `fossps check` runs the start handler and 60 ticks with no window and nothing pressed, and exits 1 on any script error. It exists so an assistant or CI can verify a script change; it says plainly that input-only code was not run. Pressing actions during a check is a follow-up.
- 2026-11-13 — glTF loading (#5) was split: reading the file into plain data is its own crate, `fossps-assets`, with no graphics card involved, because the dedicated server needs level shapes for collision. Drawing (#58), PBR shading (#59) and the game-folder and script surface (#60) follow.
- 2026-11-13 — `fossps-assets` parses with the `gltf` crate but does its own file reading: a level may only read files in or below its own folder (a downloaded map cannot name `../` or absolute paths), and pictures are decoded only with the default `textures` feature, so a server links no image decoders. Every data range is checked before the `gltf` reader touches it, since that reader trusts the file.
- 2026-11-13 — glTF's directions and units are the engine's: +Y up, -Z forward, +X right, metres. Nothing is converted on load, so numbers in Blender's glTF export and in the engine agree.
- 2026-11-13 — Only PNG and JPEG textures and uncompressed meshes are read. A file that needs Draco, meshopt, quantization or KTX2/WebP is refused with the export option to change, not half-loaded; those decoders can come later if levels need them.
- 2026-11-13 — A shape with no material is matte white (metallic 0, roughness 1), not glTF's default of full metal, which looks black under simple lighting; blockout levels have no materials.
- 2026-11-13 — Missing normals are worked out flat (points shared between faces are split), and missing tangents with MikkTSpace (`bevy_mikktspace`, pure Rust) only for parts whose material has a normal map. Skins, animations, points and lines are skipped with a warning, not an error.
- 2026-11-13 — Collision and the character controller (#6) are their own crate, `fossps-physics`, with no window, input or script code in it: a server, a predicting client and `fossps check` all step the same `Player`. Driving it from actions, the camera and the script surface is #64, which needs #58 and #60.
- 2026-11-13 — `parry3d` answers only "what does this shape hit in the level's triangles"; the controller itself is ours. Rapier's ready-made controller brings a whole physics world and is not tuned like a shooter, and writing swept collision and a triangle tree by hand is weeks of edge cases parry already has. No parry type appears in the crate's public surface, so it can be replaced.
- 2026-11-13 — The player is a capsule (0.35 m radius, 1.8 m standing, 1.1 m crouched). A flat-bottomed cylinder was tried because it climbs stairs like Quake's box, but parry reports touch directions up to 70 degrees wrong where a flat base meets the corner of a floor triangle; a capsule's are exact. The capsule's round base is handled instead: resting on an edge counts as ground when the surface past the edge is flat, and a step up always reaches far enough to get over the lip.
- 2026-11-13 — Movement is Quake's friction-and-accelerate model (walk 4.5, sprint 6.5, crouch 2.0 m/s, 1.1 m jump, gravity 20, weak air steering, 0.4 m steps, 45 degree slopes), with two changes: how hard the ground pushes depends on the stance's top speed rather than the wished speed, so a half-pushed stick walks at half speed instead of not moving, and walking follows a ramp at full speed in the direction faced. Holding jump does not jump again on landing.
- 2026-11-13 — The player keeps 1 cm clear of every surface, and a move looks that far past its end. Parry's directions are unreliable for a shape that starts a move touching something, and without the look-ahead a slow walker never registers the stair in front of them.
- 2026-11-13 — Movement uses software sine and cosine (`libm`) and parry's `enhanced-determinism`, so the same inputs give the same bits on one machine (tested) and are meant to across machines. That x86 and ARM agree bit for bit is not verified; the netcode (#11) must correct small differences rather than assume none.
- 2026-11-13 — Weapons (#7) are their own crate, `fossps-weapons`, with no window, input or script code in it, like movement: a server, a predicting client and `fossps check` step the same `Weapon` and `Projectile`. Putting one in the player's hands and the script surface is #66, which needs #64.
- 2026-11-13 — A weapon keeps the time until its next shot and carries the leftover from tick to tick, so 800 rounds a minute is 800 at any tick rate (gaps alternate 4 and 5 ticks at 60 Hz) and a fast weapon fires several times in one tick. Time spent not firing is never saved up, and one tick fires at most 8 shots.
- 2026-11-13 — Weapons keep no random number generator. Every roll comes from `shot_seed(player, tick)` handed to `Weapon::step`, as Source derives its from the command number, so a server and a client fire the same bullets and a replayed tick rolls the same way.
- 2026-11-13 — Recoil moves the view and bullets leave along the moved view (`Weapon::kick` is added to the camera), so the centre of the screen is always where the next shot goes; spread is a separate cone around it that widens with firing, movement and jumping. Recoil is a fixed kick up plus a rolled sideways kick; a learnable per-shot pattern is #67.
- 2026-11-13 — Reloads hand over their rounds 75% of the way through and a reload cut short before that gives nothing. A magazine holds exactly `magazine_size` unless `keeps_chambered_round` is set, because "30 means 30" is easier to explain. Holding the trigger on an empty magazine reloads.
- 2026-11-13 — Players are shot as upright capsules, hit zones by height (top 15% head, bottom 45% legs) until skeletons exist (#68). Rockets, grenades and slow bullets are points swept along their whole path each tick, so nothing fast passes through a wall; a bounce drops the rest of that tick. `fossps-physics` gained one public question for this, `Level::raycast`.
- 2026-11-13 — The weapon numbers (rifle 750 rpm, 30 damage falling to 21 between 25 and 60 m, and the rest) are starting estimates, not taken from a shipped game or playtested; the research behind the design leaned on recalled knowledge of Source and Quake, with only Valve's prediction pages and Riot's netcode posts checked.
- 2026-11-13 — Any frame rate (#70–#76): the game steps on fixed ticks and the picture is blended between them; only the view angles update every drawn frame. Scripts get a fixed-rate tick handler for rules and a per-frame handler for visuals, with built-in timers, so nobody multiplies by delta time. No closed latency SDK is linked: Anti-Lag 2 is MIT, and Reflex is used only if the plain Vulkan extension is enough.
- 2026-11-13 — `fossps package` never compiles (#18, #77–#83): it stamps a game pack onto ready-made engine builds fetched once and checked by hash, so no Rust toolchain is needed and any system packages for all three. The pack sits beside the Windows `.exe` and inside the macOS `.app` by default, because data glued onto a program breaks code signing; one glued file is an option.
- 2026-11-13 — "Lossless by default" (#84) means what the engine loads from a pack is bit-for-bit what it loads from the folder: zstd, smaller PNGs, the meshoptimizer codec without rounding, FLAC. GPU texture formats and Opus change the data, so they are the opt-in `--smaller` (#85) even though they load faster; the owner asked for lossless first. Scripts ship as source, since Luau bytecode cannot be trusted from mods.
- 2026-11-13 — The editor's "no CSG brushes" rule is narrowed to "no boolean modelling" (#87, #88): blockout shapes stay simple solid blocks whose faces can be pulled, and doors and windows split a wall rather than subtract from it. More editor work (#87–#99) keeps the FPS-only rule; bots must use the players' own movement code or their findings mean nothing.
- 2026-11-13 — Script editing (M6, #100–#107): the creator's own editor comes first (VS Code extension, debugger), and all tools read the running game through one local link. The built-in script panel is deliberately small (errors on the line, live values, draggable numbers) and uses the UI toolkit's text box; a full code editor is declined as general-purpose work. Other tools (#108–#114) are small and FPS-specific.
- 2026-11-13 — The owner reversed two packaging defaults the same day. Shrinking that changes assets (GPU texture formats, Opus, rounded mesh positions, #85) is on by default because it is smaller, loads faster and uses less video memory; `fossps package --exact` keeps everything bit-for-bit (#84). The Windows build is one `.exe` with the pack glued on; `--separate-pack` is for people who code-sign (#81). The entries above describe the earlier defaults.
