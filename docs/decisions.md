# Decisions

One dated line per non-obvious choice. Newest at the bottom.

- 2026-11-13 — Input lives in `fossps-input`, a crate with no platform dependencies, so the dedicated server, replays and tests use the same `InputFrame` without linking a window system.
- 2026-11-13 — Windowing is winit 0.30 and gamepads are gilrs 0.11, both behind the `window` feature of `fossps` (on by default) so a headless build links neither.
- 2026-11-13 — Keys are bound by physical position, not by the letter printed on them, so WASD works on AZERTY and Dvorak.
- 2026-11-13 — Gamepad buttons are named by position (`GamepadSouth`), not by Xbox or PlayStation labels.
- 2026-11-13 — An action has one of three kinds (button, 1D axis, 2D axis). No Unreal-style modifier and trigger stacks: too much to learn for the "Easy" pillar.
- 2026-11-13 — `look` is one action with two readings: mouse movement in raw counts (`delta`, never scaled by time) and stick tilt as a rate (`axis2d`). The game applies a separate sensitivity to each.
- 2026-11-13 — When several bindings drive one axis the strongest wins; they are not added, so keyboard plus stick is never faster than either.
- 2026-11-13 — Sticks use a circular scaled dead zone (inner 0.15, outer 0.95); triggers press at 0.5 and release at 0.4. gilrs's own filters are off so shaping happens once, in testable code.
- 2026-11-13 — Presses are latched per button between ticks: a tap shorter than a tick still counts once, and extra ticks in one frame do not repeat it.
- 2026-11-13 — A missing gamepad or keyboard binding is a startup warning, not an error, so a half-finished prototype still runs.
- 2026-11-13 — All connected gamepads feed one player; the active pad is the one last pushed firmly (past half way), so drift on an idle pad cannot take over. Gamepad input is ignored while the window is unfocused.
- 2026-11-13 — Simulation defaults to 60 ticks per second, with at most 5 catch-up ticks per frame and stalls over 250 ms dropped.
- 2026-11-13 — Until the renderer exists the main loop sleeps until the next tick, and `softbuffer` fills the window with a solid colour because Wayland hides windows that have drawn nothing. Both are replaced in #2. (Done: superseded by the renderer entries below.)
- 2026-11-13 — Escape always frees the mouse (and still reaches the action map); the click that captures the mouse is not passed to the game.
- 2026-11-13 — The renderer is its own crate, `fossps-render`, on `ash` 0.38 with the `loaded` feature: raw Vulkan handles stay reachable for FSR, and building needs no Vulkan SDK because the library is found at startup.
- 2026-11-13 — Shaders are WGSL compiled to SPIR-V by `naga` in `build.rs`: pure Rust, so no `glslc` or SDK to install. Revisit if a technique needs something naga cannot express.
- 2026-11-13 — Dynamic rendering and synchronization2 (both core in Vulkan 1.3) are required from the start; there are no render pass or framebuffer objects.
- 2026-11-13 — GPU choice: dedicated over built-in over software, first listed wins a tie. When none qualifies the error lists every card with its reason.
- 2026-11-13 — `vsync` (default on) is the one display setting: on is FIFO; off is MAILBOX, else IMMEDIATE, else FIFO. No frame limiter yet (added by #31, below).
- 2026-11-13 — Frames are drawn in `RedrawRequested`, requested after each loop pass. Acquiring an image times out after 100 ms and a skipped frame pauses drawing for 250 ms, so a hidden window cannot stall the simulation.
- 2026-11-13 — The swapchain is rebuilt on resize or `OUT_OF_DATE` only, never on `SUBOPTIMAL` alone, which can persist and cause a rebuild loop.
- 2026-11-13 — The triangle is tested by drawing it without a window and checking pixels. The test skips where Vulkan 1.3 is missing unless `FOSSPS_REQUIRE_VULKAN=1`, which Linux CI sets after installing lavapipe.
- 2026-11-13 — Scripting is its own crate, `fossps-script`, on `mlua` 0.12 with the `luau` feature. Luau is compiled from source, so building now needs a C++ compiler.
- 2026-11-13 — Scripts get a ready-made `game` global instead of `require("fossps")`: one line less to learn, and the Luau language server types globals from one definitions file with no per-project setup.
- 2026-11-13 — Scripts register functions (`game.onTick(function(step) ... end)`) rather than defining magic global names like LÖVE's `love.update`: a misspelled name is an error with a suggestion instead of silence, and editors can type the handler's arguments.
- 2026-11-13 — Reading a member of `game` that does not exist is an error naming the closest real one; `game` is read-only.
- 2026-11-13 — Each reload runs the saved file in a brand-new sandboxed VM. Script variables reset; engine state is untouched. `onStart` does not run again, `onReload` does. Keeping chosen script values across reloads is a follow-up.
- 2026-11-13 — A reload that fails keeps the previous version running. A runtime error in one handler is reported once per version and the other handlers keep running.
- 2026-11-13 — Saves are found by checking the file's time and size every 100 ms, and loaded once two checks agree. No file-watcher dependency: polling behaves the same on every platform and with editors that save by rename.
- 2026-11-13 — One call into a script may run for 1 second and a script may use 256 MB. A script stopped for running too long is paused until the next save, so an endless loop cannot freeze the game on every tick; catching the stop with `pcall` does not avoid it.
- 2026-11-13 — `require` is not available yet (a game is one `main.luau`); calling it says so. Multi-file games are a follow-up.
- 2026-11-13 — `fossps <folder>` plays the game in that folder, and plain `fossps` plays the current folder if it has a `main.luau`; otherwise it shows the input demo. #4 replaces this with `fossps run`.
- 2026-11-13 — The command line is parsed by `clap` (help text and "did you mean" for free), behind a `cli` feature so a game written in Rust against the library does not build it. `fossps` alone prints help and succeeds; the old `fossps <folder>` form is gone in favour of `fossps run [folder]`, and the input demo is `fossps demo`.
- 2026-11-13 — `fossps new <folder>` never asks questions, never overwrites (an empty folder is fine, one with files is refused) and does not run `git init`: a tutorial command must behave the same for everyone, and git may not be installed.
- 2026-11-13 — A new game is four files: `main.luau`, `README.md`, `fossps.d.luau` and `.vscode/settings.json` (luau-lsp `platform.type: standard` plus `types.definitionFiles`, the map form current in luau-lsp 1.70). No `.luaurc` or `.gitignore`: neither does anything yet, and every extra file is one more thing to wonder about.
- 2026-11-13 — Game names may have spaces, capitals and non-English letters; only what breaks a folder name on some platform is refused (Windows' forbidden characters and reserved names, a leading dash or dot, trailing dot or space, over 64 characters).
- 2026-11-13 — `fossps run` rewrites a game's `fossps.d.luau` when it differs from the engine's, and says so: the file is the engine's, and stale autocomplete after an upgrade is worse than a rewritten generated file. A game without the file does not get one.
- 2026-11-13 — `examples/hello/main.luau` is the template with the name filled in, held equal by a test, so the example in the repo cannot drift from what `fossps new` writes.
- 2026-11-13 — A graphical editor is planned as the last milestone (M5, #38–#44), after the engine ships. It stays inside the Focused pillar: FPS maps and game modes only, a mode of the same binary (`fossps edit`), levels stay plain glTF with entities in a text file beside them, and no CSG brushes, terrain, material graphs or visual scripting.
- 2026-11-13 — The editor is kept easy by three rules (#46–#53): the game mode tells you what the map still needs, tools use the player's own measurements and controls, and anything advanced is an overlay or a search away rather than a permanent panel. These ideas were not checked against prior art when filed; each issue does that first.
- 2026-11-13 — New games ship a `CLAUDE.md` and a `.claude/settings.json` that pre-approves only `fossps check`. The guide points at `fossps.d.luau` as the one list of what exists, so it does not go stale when the API grows; unlike that file it belongs to the game's author and is never rewritten.
- 2026-11-13 — `fossps check` runs the start handler and 60 ticks with no window and nothing pressed, and exits 1 on any script error. It exists so an assistant or CI can verify a script change; it says plainly that input-only code was not run. Pressing actions during a check is a follow-up.
- 2026-11-13 — glTF loading (#5) was split: reading the file into plain data is its own crate, `fossps-assets`, with no graphics card involved, because the dedicated server needs level shapes for collision. Drawing (#58), PBR shading (#59) and the game-folder and script surface (#60) follow.
- 2026-11-13 — `fossps-assets` parses with the `gltf` crate but does its own file reading: a level may only read files in or below its own folder (a downloaded map cannot name `../` or absolute paths), and pictures are decoded only with the default `textures` feature, so a server links no image decoders. Every data range is checked before the `gltf` reader touches it, since that reader trusts the file.
- 2026-11-13 — glTF's directions and units are the engine's: +Y up, -Z forward, +X right, metres. Nothing is converted on load, so numbers in Blender's glTF export and in the engine agree.
- 2026-11-13 — Only PNG and JPEG textures and uncompressed meshes are read. A file that needs Draco, meshopt, quantization or KTX2/WebP is refused with the export option to change, not half-loaded; those decoders can come later if levels need them.
- 2026-11-13 — A shape with no material is matte white (metallic 0, roughness 1), not glTF's default of full metal, which looks black under simple lighting; blockout levels have no materials.
- 2026-11-13 — Missing normals are worked out flat (points shared between faces are split), and missing tangents with MikkTSpace (`bevy_mikktspace`, pure Rust) only for parts whose material has a normal map. Skins, animations, points and lines are skipped with a warning, not an error.
- 2026-11-13 — Collision and the character controller (#6) are their own crate, `fossps-physics`, with no window, input or script code in it: a server, a predicting client and `fossps check` all step the same `Player`. Driving it from actions, the camera and the script surface is #64, which needs #58 and #60.
- 2026-11-13 — `parry3d` answers only "what does this shape hit in the level's triangles"; the controller itself is ours. Rapier's ready-made controller brings a whole physics world and is not tuned like a shooter, and writing swept collision and a triangle tree by hand is weeks of edge cases parry already has. No parry type appears in the crate's public surface, so it can be replaced.
- 2026-11-13 — The player is a capsule (0.35 m radius, 1.8 m standing, 1.1 m crouched). A flat-bottomed cylinder was tried because it climbs stairs like Quake's box, but parry reports touch directions up to 70 degrees wrong where a flat base meets the corner of a floor triangle; a capsule's are exact. The capsule's round base is handled instead: resting on an edge counts as ground when the surface past the edge is flat, and a step up always reaches far enough to get over the lip.
- 2026-11-13 — Movement is Quake's friction-and-accelerate model (walk 4.5, sprint 6.5, crouch 2.0 m/s, 1.1 m jump, gravity 20, weak air steering, 0.4 m steps, 45 degree slopes), with two changes: how hard the ground pushes depends on the stance's top speed rather than the wished speed, so a half-pushed stick walks at half speed instead of not moving, and walking follows a ramp at full speed in the direction faced. Holding jump does not jump again on landing.
- 2026-11-13 — The player keeps 1 cm clear of every surface, and a move looks that far past its end. Parry's directions are unreliable for a shape that starts a move touching something, and without the look-ahead a slow walker never registers the stair in front of them.
- 2026-11-13 — Movement uses software sine and cosine (`libm`) and parry's `enhanced-determinism`, so the same inputs give the same bits on one machine (tested) and are meant to across machines. That x86 and ARM agree bit for bit is not verified; the netcode (#11) must correct small differences rather than assume none.
- 2026-11-13 — Weapons (#7) are their own crate, `fossps-weapons`, with no window, input or script code in it, like movement: a server, a predicting client and `fossps check` step the same `Weapon` and `Projectile`. Putting one in the player's hands and the script surface is #66, which needs #64.
- 2026-11-13 — A weapon keeps the time until its next shot and carries the leftover from tick to tick, so 800 rounds a minute is 800 at any tick rate (gaps alternate 4 and 5 ticks at 60 Hz) and a fast weapon fires several times in one tick. Time spent not firing is never saved up, and one tick fires at most 8 shots.
- 2026-11-13 — Weapons keep no random number generator. Every roll comes from `shot_seed(player, tick)` handed to `Weapon::step`, as Source derives its from the command number, so a server and a client fire the same bullets and a replayed tick rolls the same way.
- 2026-11-13 — Recoil moves the view and bullets leave along the moved view (`Weapon::kick` is added to the camera), so the centre of the screen is always where the next shot goes; spread is a separate cone around it that widens with firing, movement and jumping. Recoil is a fixed kick up plus a rolled sideways kick; a learnable per-shot pattern is #67.
- 2026-11-13 — Reloads hand over their rounds 75% of the way through and a reload cut short before that gives nothing. A magazine holds exactly `magazine_size` unless `keeps_chambered_round` is set, because "30 means 30" is easier to explain. Holding the trigger on an empty magazine reloads.
- 2026-11-13 — Players are shot as upright capsules, hit zones by height (top 15% head, bottom 45% legs) until skeletons exist (#68). Rockets, grenades and slow bullets are points swept along their whole path each tick, so nothing fast passes through a wall; a bounce drops the rest of that tick. `fossps-physics` gained one public question for this, `Level::raycast`.
- 2026-11-13 — The weapon numbers (rifle 750 rpm, 30 damage falling to 21 between 25 and 60 m, and the rest) are starting estimates, not taken from a shipped game or playtested; the research behind the design leaned on recalled knowledge of Source and Quake, with only Valve's prediction pages and Riot's netcode posts checked.
- 2026-11-13 — Any frame rate (#70–#76): the game steps on fixed ticks and the picture is blended between them; only the view angles update every drawn frame. Scripts get a fixed-rate tick handler for rules and a per-frame handler for visuals, with built-in timers, so nobody multiplies by delta time. No closed latency SDK is linked: Anti-Lag 2 is MIT, and Reflex is used only if the plain Vulkan extension is enough.
- 2026-11-13 — `fossps package` never compiles (#18, #77–#83): it stamps a game pack onto ready-made engine builds fetched once and checked by hash, so no Rust toolchain is needed and any system packages for all three. The pack sits beside the Windows `.exe` and inside the macOS `.app` by default, because data glued onto a program breaks code signing; one glued file is an option.
- 2026-11-13 — "Lossless by default" (#84) means what the engine loads from a pack is bit-for-bit what it loads from the folder: zstd, smaller PNGs, the meshoptimizer codec without rounding, FLAC. GPU texture formats and Opus change the data, so they are the opt-in `--smaller` (#85) even though they load faster; the owner asked for lossless first. Scripts ship as source, since Luau bytecode cannot be trusted from mods.
- 2026-11-13 — The editor's "no CSG brushes" rule is narrowed to "no boolean modelling" (#87, #88): blockout shapes stay simple solid blocks whose faces can be pulled, and doors and windows split a wall rather than subtract from it. More editor work (#87–#99) keeps the FPS-only rule; bots must use the players' own movement code or their findings mean nothing.
- 2026-11-13 — Script editing (M6, #100–#107): the creator's own editor comes first (VS Code extension, debugger), and all tools read the running game through one local link. The built-in script panel is deliberately small (errors on the line, live values, draggable numbers) and uses the UI toolkit's text box; a full code editor is declined as general-purpose work. Other tools (#108–#114) are small and FPS-specific.
- 2026-11-13 — The owner reversed two packaging defaults the same day. Shrinking that changes assets (GPU texture formats, Opus, rounded mesh positions, #85) is on by default because it is smaller, loads faster and uses less video memory; `fossps package --exact` keeps everything bit-for-bit (#84). The Windows build is one `.exe` with the pack glued on; `--separate-pack` is for people who code-sign (#81). The entries above describe the earlier defaults.
- 2026-11-13 — The owner then reverted the Windows half of the entry above: the default is again `Game.exe` with `Game.fpk` beside it, so the exe can be code-signed, and `--single-file` is the option (#81). Asset shrinking by default (#85) stands.
- 2026-11-13 — Linux games package as a plain `.tar.gz` (program, pack, icon) by default; an AppImage is the option `--appimage` (#121). Stores and patchers want loose files, the engine has few libraries to bundle, AppImages need FUSE, and the pack is already compressed. MangoHud is not bundled: players who want it have it, and the engine's own frame-time graph (#75) works on every system.
- 2026-11-13 — HUD and menus (#8) were split like movement and weapons: `fossps-ui` is its own crate with no window, graphics or script code. It takes a plain `UiInput` and gives back events and a list of boxes and text, so menus are tested without a graphics card. Drawing (#124), the running game and a built-in pause menu (#125), the script surface (#126) and scrolling and button hints (#127) follow.
- 2026-11-13 — Widgets are kept between frames (a retained tree), not rebuilt every frame: which widget the player is on, each screen's remembered place and the stack of open screens have to live somewhere, and a beginner's script should not have to carry them. Events come back from `Ui::update` as a list rather than through callbacks, so the script layer can turn them into handlers.
- 2026-11-13 — A direction press goes to the widget with the lowest cost among those whose middle is past the current widget's edge: distance ahead, plus twice the distance sideways, minus how much the two line up. This is a cut-down form of the W3C spatial navigation draft's formula. Nobody has to wire up neighbours, so a menu cannot be built that a gamepad cannot reach; `neighbor` overrides one link when the automatic pick is wrong. Lists wrap round by default.
- 2026-11-13 — A held direction repeats after 0.4 s and then every 0.1 s, and a stick counts past halfway. These are our picks, not numbers confirmed from a shipped engine. After the mouse was used, the first gamepad or keyboard press only brings the outline back; it does not move or choose anything the player cannot see.
- 2026-11-13 — UI sizes are pixels on a screen 1080 high, scaled by the real height and the player's size setting (0.75 to 1.5). The HUD stays inside the middle 90% (the title-safe area in Xbox's guidance) and text is never under 24 px at 1080. HUD offsets are always right and down, not "inwards", so one rule covers all nine anchors.
- 2026-11-13 — Back always closes the screen on show, including the last one; a main menu opts out with `stays_open`. Only the top screen is drawn. Tabs are switched with the shoulder buttons or a click and cannot be landed on with the d-pad, so left and right stay free for sliders and choices.
- 2026-11-13 — Sound (#9) was split like movement, weapons and the HUD: `fossps-audio` is its own crate with no game-loop or script code. We wrote the mixer instead of using `kira` or `rodio` (both sit on `cpal` too) so that it fills a plain buffer, is tested with no sound card, never allocates, and gives the same numbers however the stream is cut into buffers. `cpal` 0.18 sends it to the device behind the `device` feature; requests cross to the sound thread on an `rtrb` queue and finished sounds come back the same way, so that thread never locks or frees. The running game (#129), scripts (#130) and Ogg and music (#131) follow.
- 2026-11-13 — A placed sound halves in volume each time the distance doubles (OpenAL's clamped inverse-distance model), fades out over the last tenth of its range, is shared between the ears at equal power, and behind the listener is 30% quieter with a 4 kHz low-pass. No HRTF and no delay between the ears: little gain on speakers. Occlusion by walls is #132. The 30%, the 4 kHz, the 5 ms fades and the ranges (footsteps 30 m, gunfire 150 m, other sounds 50 m) are our picks from recalled OpenAL, FMOD and Source defaults, not verified numbers.
- 2026-11-13 — With every voice busy (64 by default) a new sound takes the least important, then quietest, then oldest voice, and is skipped if it would be the quietest itself. The voice it takes fades out over 5 ms into a side buffer, so stealing never clicks. A one-shot sound started out of earshot is not played at all.
- 2026-11-13 — Footsteps come by distance covered (2 m walking, 2.2 m sprinting, 1.3 m crouched: about 2.2, 3 and 1.5 steps a second at the default speeds), not by a timer, and crouched steps are a quarter as loud, so crouching is how to sneak. `Footsteps` takes a plain `Feet` value so the sound crate does not depend on physics. Which take plays and its pitch and volume shift come from a seed the caller passes (the tick) and the take played before, so the same run of sounds always comes out the same.
- 2026-11-13 — The engine makes its own footstep, gunshot, landing, dry-fire and reload sounds from arithmetic (`fossps_audio::starter`), so a new game is not silent and no sound files with licences of their own ship with it. They are stand-ins. Only WAV loads for now (`hound`, Apache-2.0); building on Linux now needs the ALSA headers.
- 2026-11-13 — The dedicated server (#10) is `fossps::server::serve` plus two ways to start it: `fossps serve`, so a creator needs nothing new, and a separate `fossps-server` program built without the `window` feature, so a hosting machine gets no windowing, graphics, gamepad or sound code (a test reads `cargo tree` to keep it that way). Neither takes a tick-rate option: `fossps run` has none either, and a server ticking at a different rate from its players would be a trap once they can join (#11).
- 2026-11-13 — Between ticks the server only sleeps; it does not spin on the clock for the last millisecond, which would cost about 6% of a core per idle server. Real time is banked in the same `TickClock` the window uses, so a sleep that runs long is made up by the next one and the rate does not drift. Rust's `thread::sleep` uses Windows' high-resolution timer (per the std source; the exact Windows version it needs was not checked). A server that is behind runs at most 5 ticks in a row, gives up the rest and warns at most every 10 s, saying whether its own ticks were slow or the machine stalled. The 5, the 10 s and the one-minute status line are our picks.
- 2026-11-13 — Ctrl-C, SIGTERM, SIGHUP and closing the console all stop the server after the tick it is in, with exit code 0, through the `ctrlc` crate (MIT OR Apache-2.0, `termination` feature) rather than `signal-hook`, which is Unix-only.
- 2026-11-14 — Netcode (#11) was split like movement, weapons, the HUD and sound: `fossps-net` is its own crate that only makes and reads packets. It opens no socket and reads no clock, so prediction and correction are tested over a hand-built connection that loses, delays, repeats and reorders packets. UDP and joining (#161), the running game (#162), smoothing other players (#163) and holding the command buffer steady by nudging the client's tick rate (#164) follow.
- 2026-11-14 — A client sends each tick's input rounded to 8 bytes (stick axes to 1/127, yaw to 1/65536 of a turn) and moves its own player with the rounded input, so server and client run the very same numbers and a correct prediction matches exactly; a snapshot carries the client's own player in full `f32`s and the client replays on any difference at all. Each packet repeats the last 3 commands (our pick; lightyear repeats inputs but gives no count). The server runs one command per player per tick whatever is sent, keeps at most 8 waiting, waits for 2 before starting and after running dry, drops the oldest when more than 4 wait so a burst does not leave a player behind for good (our picks), and repeats a late player's last command without fire for 5 ticks before letting go of their keys (our pick).
- 2026-11-14 — Other players go out rounded (position to 1/512 m in 24 bits per axis as in Fiedler's snapshot compression, yaw and pitch 16 bits each) and as changes from the newest snapshot the client has acknowledged, or whole when that is more than 32 ticks old (Quake 3's scheme and number). The acknowledgement rides in the command packet. 64 players, all changed, fit one 1200-byte packet, so nothing is ever split; 64 is therefore the limit for now. Corrections ease out on screen over 0.1 s and anything over 2 m is shown at once (our picks; Valve's `cl_smooth` values could not be read). Tick and command numbers are plain `u32`s with no wrap-around: 2.2 years at 60 ticks a second.
- 2026-11-14 — Lag compensation (#12): each command says which snapshot tick the player had on screen (plus 256ths towards the next, for when others are drawn between snapshots, #163), and `Server::seen_by` gives the others as they were then, blended between the two ticks. The client says the tick, as in Source's `tick_count` and Valorant, because this crate reads no clock to estimate latency with; the server only believes a view that is no newer than the newest snapshot the packet says was read, never goes back in time, and is at most `rewind_limit` old: 0.2 s by default, the window Source checks a claimed tick against. Past the limit the shooter has to lead. Nobody is put back to before they joined or moved over 2 m in one tick (a respawn or teleport; Source's `sv_lagcompensation_teleport_dist` idea, our number), the shooter is never moved back, and rockets and grenades fly through the present, as in TF2. Commands grow from 8 to 13 bytes; the packet version is 2.
- 2026-11-14 — Game modes (#13) were split like the other systems: `fossps-mode` is its own crate holding the match (teams, score, round clock, respawns, spawn choice) with no script, clock or map code, and `fossps-script` puts it in front of Luau. The match lives in the script host, outside the Luau VM, so saving a script keeps the score; new numbers apply at once and only a changed team list starts the match again. The running game (#171), the scoreboard (#172) and line of sight in spawn choice (#173) follow. Until #171, the rules are driven by tests and by `fossps check`, which now plays a pretend two-player match so every `game.on...` function is called.
- 2026-11-14 — A mode is numbers plus events, as Counter-Strike splits `mp_` settings from game events and as Core keeps team scores in the engine (`Game.IncreaseTeamScore`): `game.mode { teams, scoreToWin, killPoints, timeLimit, respawnDelay, warmup, intermission }` is a whole deathmatch with no other code, and `game.onKill` and friends only add to it. The engine scores kills itself (`killPoints`, 1 by default, 0 to switch off; nothing for a team-mate or yourself) and owns the respawn timer, so no script hand-writes a counter or a `wait()` loop. What a handler returns is ignored, unlike Garry's Mod hooks, and there is no magic name like Roblox's `leaderstats`. Left out for now as not needed for deathmatch: moving a player between teams, respawning from a script, the round's number.
- 2026-11-14 — Mode defaults: first to 50, ten minutes, 3 s respawn, 5 s warm-up, 10 s intermission, at most 8 teams. These are our picks from typical team-deathmatch settings, not numbers confirmed from a shipped game. Scores only count while a round is played, so the final score cannot change in the intermission; a round ends the moment a score reaches the target; equal scores when time runs out are a draw. A new player goes to the smallest team, then the lowest-scoring, then the first listed.
- 2026-11-14 — What a handler does to the match (a score that ends the round) is queued and told to the script after the handler returns, so handlers never run inside each other; 10 000 events in one go is treated as handlers setting each other off and the rest are skipped with an error. A player is one Luau value for as long as they are in the match, so `streak[player]` and `==` work; after they leave, reading it is an error that says so. `game.round.phase()` and `game.round.timeLeft()` are functions although a player's score is read without brackets: in a sandboxed VM Luau looks up `game.round.phase` once when the file loads, so a value there would never change (tried, and it stayed "waiting"). Players and teams are userdata with a colon for actions (`team:addScore(1)`) and an error that says "needs a colon" for a dot.
- 2026-11-14 — A spawn point is chosen by distance to the nearest enemy, the further the better up to 40 m (Quake 3 picks among the furthest points; Halo's write-ups describe enemies pushing spawns away), by chance among the points at least three quarters as good as the best, never on top of another player while a point is free, and on the team's own points where the map has them. The numbers are ours. "Did you mean" now counts two swapped letters as one slip, so `Bleu` finds `Blue`.
- 2026-11-14 — UDP (#161) lives in `fossps-net` as `UdpHost` and `UdpLink` on std's `UdpSocket`, with no new dependency and no thread: `poll` never waits, so both sit in the tick. The join rules underneath take the datagram and the time as arguments and are tested with no network. Joining is four datagrams. The request is padded to 1200 bytes (QUIC's rule for a first datagram, RFC 9000 §14.1; netcode.io: "any response packet is smaller than the request"), the server's answer is a SipHash of the address, the player's own random number and an 8-second period under a secret made at start-up (std's `RandomState`), and the server keeps nothing until that number comes back, so it cannot be used to flood a third party. netcode.io does keep state at that point; keeping none is our choice, as in QUIC's Retry. The same number then rides in every datagram (10 bytes of wrapping), so knowing a player's address is not enough to send commands for them. A player whose address changes mid-game is dropped and must rejoin; QUIC-style migration was left out.
- 2026-11-14 — Transport numbers: a joining player asks ten times a second (netcode.io's "like 10HZ") for 5 s; 10 s of silence drops a player or ends a game for one; a goodbye is sent 3 times; a number from the server is good for 8 to 16 s; the last 64 players to leave are remembered so a late copy of their joining datagram does not put them back. All but the first are our picks: Quake 3 waits 200 s and ENet 5 to 30 s, and netcode.io gives no default. Windows reports "nobody was listening" for an earlier datagram as an error on the next read (KB 263823), so read errors are stepped over, 16 at most per poll. One address and port holds one place at a time, a poll reads at most 1024 datagrams so a flood cannot hold up the tick, and a name with both kinds of address is joined over IPv4, because `localhost` often lists `::1` first and a server opened on `0.0.0.0` does not hear it (our picks).

- 2026-11-15 — Rumble (#28) is `game.input.rumble(strong, weak, seconds)`: the heavy and the light motor from 0 to 1, then how long. - 2026-11-15 — Rumble is played with gilrs force feedback, which works on Linux (evdev) and Windows and not on macOS, where a call does nothing (#210). Its `Repeat::For(n)` alone plays two steps (100 ms) longer than asked, which would double a shot's rumble, so each motor is given a wait longer than any rumble before it would start again and the effect is ended on the step the motors go quiet. Rust games ask from `Frame::rumble`, like action sets: it is about the player at this computer, not the simulation. A script's rumble therefore reaches the player only where the script runs on their computer (`fossps run`); `player:rumble` sent to a joined player's computer is #211, and a setting for the player to turn rumble down or off, which the Xbox and Game Accessibility guidelines ask for, is #212. - 2026-11-15 — The frame rate limit (#31) is `Config::max_fps`, with 0 for no limit, the name and the convention of Godot's `max_fps` and Source's `fps_max`. The default is 400 (what CS2 is reported to ship with), not 0: with vsync off an unlimited loop drew the triangle 22,000 times a second, and a game should not need a setting to stop that. It applies with vsync on too, where it only matters when lower than the display's rate. A limit from 1 to 29 is raised to 30, because the loop runs at most five ticks a frame and slower frames would leave ticks behind. Players cannot change `vsync` or `max_fps` yet; that comes with the settings file.
- 2026-11-15 — The limit is waited out at the top of the loop, before input is read and the game is asked for a frame, so the picture is as fresh as it can be (NVIDIA's advice for low latency is to delay input sampling and simulation rather than wait after drawing, which would show older input). Frames are due at fixed times from each other, not a fixed time after the last one started, so a late wake does not lower the rate, and a stall is not made up with a burst (`spin_sleep` and `bevy_framepace` schedule the same way). The event loop sleeps until 0.2 ms before a frame is due and then watches the clock: our pick, shorter than the 1 ms or so `spin_sleep` can pick on Windows, because without vsync a frame a fraction of a millisecond out cannot be seen, and a longer watch costs a real share of a core at 400 frames a second. No new crate.
- 2026-11-15 — "No validation mistakes" in a drawing test only means something if the layer was loaded, so `FOSSPS_REQUIRE_VALIDATION=1` makes those tests (`fossps-render`, `fossps-fsr`) fail when it is not, and Linux CI sets it beside `FOSSPS_REQUIRE_VULKAN`. It is a test switch only: a game never refuses to start over a missing layer.
- 2026-11-15 — `require` (#32) follows Luau's own require-by-string rules so that what a beginner reads about Luau, and what the Luau language server follows in an editor, is what works: a path starts with `./` or `../`, is taken from the file that asks (not from where the game was started), has `/` between folders and may leave `.luau` off. `require("weapons")` is a mistake that is answered with `require("./weapons")`. Left out until something needs them: `@` aliases and `.luaurc`, a folder's `init.luau` (requiring a folder says to name a script in it) and `.lua` files. A script that returns nothing gives `nil` rather than Roblox's "did not return exactly one value", because a file that only adds `game.on...` functions is a fair thing to write. Each file runs once per load; two files that require each other are an error that names the circle, not a hang (Roblox) or a half-built table (Lua 5.1).
- 2026-11-15 — `require` is our own function, not mlua's `Require` trait: that one keeps its own cache in the registry and words its own errors, and we need to name every file read (to watch it), read from a pack as well as a folder, and say what to write instead. A path is turned into a name below the game's folder before anything is read, and the name is checked again where the file is opened: `..` cannot climb past the folder, the file that asks is only believed if the game really read it (`loadstring` lets a script name its own chunk), and names with a backslash, a colon, a leading dot or a Windows device name are refused. A file reached through a link is refused too, and so is one whose name on disk has other capital letters (Windows and macOS would find it): `fossps package` leaves links and hidden files out and a pack tells capitals apart, so a game that runs from its folder also runs packaged. `main.luau` cannot be required.
- 2026-11-15 — Saving any script the game read starts the whole script again in a fresh VM, as saving `main.luau` already did, rather than swapping one module in place (lurker's `lume.hotswap`, Defold): those leave other files holding the old table, which is the stale-reference trap both document. The match and its score live outside the VM and are kept. Files that were looked for and not found are watched as well, so creating the missing `weapons.luau` is picked up, and so are the files of a version that failed to load, so the fix is. A packaged game gets every `.luau` in its pack as text up front (`ScriptHost::from_sources`); nothing is watched there. An error is put down to the file its message names, and `fossps check`, `fossps package` and a packaged game name that file instead of always `main.luau`.
- 2026-11-15 — Keeping script values across a reload (#33) is `local saved = game.keep("saved", { best = 0 })`: a named table with what it starts with, and the script changes what is inside. React's `useState` and Vite's `import.meta.hot.data` have this shape, the starting values sit beside the use, and the editor knows the table's fields from them. A pair of save and restore hooks (Vite `dispose`, Defold `on_reload`, lurker) is more to write and easy to half-forget, and keeping every top-level variable by itself (Fast Refresh, `lume.hotswap`) cannot be done across VMs and surprises when it resets. Only a table can be kept: `game.keep("jumps", 0)` would hand back a number the engine never sees change, so it is an error that says to put it in a table. Kept values win over the starting ones, and keys the start now has and the kept table lacks are added (top level only, so an emptied list is not refilled); a table is started over by renaming it or restarting the game, and a name the running script did not ask for is forgotten at the next reload.
- 2026-11-15 — A kept table is copied out of the old VM as plain data just before a reload and rebuilt in the new one, because nothing can be shared between two VMs: numbers, text, true and false, vectors, tables of those, and players, who come back as the new version's value for the same player so `streaks[player]` survives, and are dropped once they have left. Functions, teams (keep `team.name`: team numbers change with `game.mode`) and tables used as keys are left out with a message naming where they are; metatables stay behind. The copy reads tables raw and is limited to 32 levels, 100,000 keys and values and 16 MB of text for all kept tables together, so a script cannot stall or bloat a reload, and a table that holds itself ends at the depth limit. If the new version fails to load, the old one carries on with its own tables. Nothing is written to disk: saving a game between runs is another feature.
- 2026-11-15 — The HUD and menus (#124) are drawn inside the tone mapping's pass, straight after its one triangle: at the window's full size after FSR, untouched by exposure, and with no extra pass or image. Each box and each letter is one instanced quad from a per-frame buffer (8192 a frame; more is left out with one warning). Boxes get their round corners and soft edges from Inigo Quilez's rounded-box distance in the fragment shader, and their edges are put on whole pixels so a two-pixel crosshair is a sharp line. `Renderer::set_ui(ui.draw())` replaces what is drawn; a game calls `Frame::draw_ui(&ui)` each frame, several UIs stack in call order, and a frame without the call shows none.
- 2026-11-15 — Text is plain coverage bitmaps in one 2048 by 1024 one-byte atlas, each letter drawn by `fontdue` (pure Rust, MIT/Apache/Zlib; `ab_glyph` is Apache-only and quiet, `swash` and `cosmic-text` are more than a one-line HUD needs) at the size it is shown, as egui, Dear ImGui and bevy do. Signed-distance fonts (Valve, Godot's MSDF, Unreal) pay off for text scaled freely in the world, not for a HUD with a handful of sizes, and cost corner sharpness and a generator. Sizes are kept to quarter pixels so a window being dragged does not ask for a new alphabet for each pixel of height, text over 256 pixels is drawn at 256, and when the atlas fills it is emptied and started again with what is on screen. Only rows that changed are sent to the graphics card. Letters stand on whole pixels. No shaping yet: one line, left to right, with the font's pair kerning.
- 2026-11-15 — The font built into the engine is Atkinson Hyperlegible Next Regular (Braille Institute, SIL OFL 1.1, no reserved name, 65 KB): `I`, `l` and `1`, and `O` and `0`, cannot be mistaken for each other, which is what an ammo count read at a glance needs. Inter and Noto Sans cover more alphabets but are several times the size and less distinct; it covers Latin only, so other alphabets wait for fallback fonts (#221). The OFL allows embedding in software under any licence if the notice and licence travel with it, so `OFL.txt` sits beside the font and goes into release archives and into every package `fossps package` writes. `Font` implements `fossps_ui::TextMeasure`, so a `Ui` given `Font::bundled()` centres text by the widths that are drawn.
- 2026-11-15 — UI colours are sRGB numbers, as designers write them. A window that stores sRGB (what the renderer asks for) is given them with the curve undone, so a solid colour comes out exactly as written and see-through edges are blended in linear light; a window that stores numbers as given gets them as they are and blends in sRGB. Solid colours match on both (tested), and only the look of half-covered pixels differs slightly. Blending in sRGB everywhere (egui's choice, for slightly heavier dark-on-light text) would need a second, non-sRGB view of every swapchain image; HUD text is light on a dark scene, where linear blending reads well, so that was left out.
- 2026-11-15 — A script error is shown over the game (#34) as a panel in the top-left corner, not a full-screen takeover: LÖVE's blue screen and Vite's modal stop everything, but here the last version that worked is still running and worth watching, so the panel sits over it as Next 15.2's corner indicator and Flutter's in-place error box do. It says, in the terminal's order, where the error is, the line of the script, what went wrong, the hint and what the engine did; it stays until a save loads the script (the script host's `last_error` clearing), with no key to dismiss it, because the fix is the save. Only a game opened from a folder shows it (`ScriptGame::open`): a packaged game's players did not write the script and cannot fix it, as Vite, Next and Flutter keep their overlays out of release builds; their error stays in the terminal. Script text is untrusted, so each part is cut at 600 characters, control characters become spaces, words longer than a line are split, and past 14 lines the panel ends with "The rest is in the terminal." It is the engine's own `fossps_ui::Ui`, drawn by `ScriptGame::frame` after everything else and built again only when the error or the window's size changes.
- 2026-11-15 — `Headless::screenshot` draws a frame and reads its pixels back, so a crate above the renderer can test what it draws (the error panel is the first); `offscreen.rs` stays the renderer's own test path.
- 2026-11-15 — The editor (#38) is the `editor` Cargo feature of the `fossps` crate, on by default so `fossps edit` works from a plain install; it needs `window`, and `fossps-server` is built without either. It is the same program and the same window loop as `fossps run`, told it is editing, not a second application. Its camera flies as the viewports of Unreal, Unity, Godot and s&box do, since someone from any of them tries that first: hold the right mouse button to look, W A S D fly along the view, E and Q go straight up and down, Shift is four times faster, the wheel changes the speed (8 m/s to start, 0.5 to 64, a quarter more a notch). Godot's Shift+F toggle was left out for being hard to find. None of those editors has a gamepad scheme to follow, so it is a shooter's: sticks fly and look, triggers down and up, left stick press faster, d-pad up and down for speed; nothing has to be held to look. The keys are written on screen with the speed, as no editor's defaults are guessable. The wheel changes speed whether or not the button is held (others dolly then), because knowing the button is held would take an action with no gamepad half. Movement is instant, without easing, and runs in ticks with frames blended between them.
- 2026-11-15 — Holding the right mouse button to look is done by the window loop in edit mode, not by an action set: a set switch deliberately ignores the button that caused it until it is pressed again, so a set cannot tell when the button is let go. The editor's actions live in one set that leaves the cursor free, which later editor tools need for pointing.
- 2026-11-15 — The ground grid is a shader (`grid.wgsl`), not line meshes: one square that follows the eye, drawn in the mesh pass after the level so it is upscaled with it and hidden by what stands on it, with lines a metre apart and stronger ones every ten (a player is 1.8 m; Unreal and Godot count the same way), X axis red and Z axis blue. Lines are drawn as Ben Golus's "pristine grid" does (never thinner than a pixel, fainter instead), which is what keeps far lines from flickering and turning to moiré; line meshes do both. It is drawn 0.2 % nearer than it is so it wins against a floor at height 0 without a depth bias that varies by graphics card, writes how far each pixel moved for FSR, and both images blend the same way (the motion with an opacity of 1) so the `independentBlend` feature is not needed. `Renderer::set_grid` and `Headless::set_grid` switch it; a game being played never draws it.
